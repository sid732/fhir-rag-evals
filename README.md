# fhir-rag-evals

A FastAPI service that answers a clinician's question about one patient's FHIR R4 record. Every sentence in an answer cites the FHIR resources it relies on, and every citation resolves to an endpoint that returns that resource. An evaluation harness measures retrieval and answer quality, and the retrieval eval gates every pull request.

All data is synthetic, generated by [Synthea](https://github.com/synthetichealth/synthea). There is no real or de-identified patient data anywhere in the project.

## Results so far

Retrieval, measured on 275 labeled questions over 15 patients (166 dev, 109 held-out test). Recall counts groups of interchangeable evidence; see [docs/evals.md](docs/evals.md).

| Configuration | Cards in context | recall@10, dev | recall@10, test |
|---|---:|---:|---:|
| BM25 | 9 | 0.571 | 0.471 |
| Dense (bge-small-en-v1.5) | 10 | 0.599 | 0.574 |
| Hybrid (BM25 + dense, RRF) | 10 | 0.616 | 0.560 |
| Hybrid + series expansion | 10 | 0.735 | 0.708 |
| Hybrid + series, same 38-card budget, no summary | 35 | 0.844 | 0.838 |
| **Hybrid + series + pinned summary (default)** | 38 | **0.951** | **0.915** |

No configuration retrieved a card from another patient's record. Full reports: [dev](evals/reports/retrieval-dev.md), [test](evals/reports/retrieval-test.md).

Answers (Opus 5.5 answering, Sonnet 5.5 judging with judge v3). Dev ran through the API; the held-out test split ran through the Claude Code CLI on a subscription ([how that differs](docs/evals.md#running-on-a-claude-subscription)). Reports: [dev](evals/reports/answers-dev-1-judge3.md), [test](evals/reports/answers-test-2.md). The dev run predates two questions added since, so it covers 164 of today's 166.

| Metric | Dev (164) | Test (109) |
|---|---:|---:|
| "Not in record" precision / recall (23 and 15 unanswerable questions) | 0.958 / 1.000 | 0.938 / 1.000 |
| Citation validity (cites only cards it was shown) | 1.000 | 1.000 |
| Citation recall | 0.957 | 0.925 |
| Numbers and dates found in the cited cards | 0.979 | 0.968 |
| Key facts present (87 and 64 value and date questions) | 1.000 | 1.000 |
| Faithfulness, judge v3 (reads about 2 points high; see below) | 0.993 | 0.986 |
| Cost per question, generator + judge | $0.040 | $0.050 at list price, not billed |
| Latency p50 / p95, whole request | 3.8 s / 8.4 s | 5.1 s / 17.3 s through the CLI |

The first test run found four wrong labels, all from templates that looked at too little of the record: three "last ER visit" questions used the last ER visit with a recorded reason instead of the last ER visit, and one "potassium" question was labeled "not in record" although the record has potassium under a second LOINC code. The model had answered all four correctly. The templates are fixed, the potassium question is gone, and the three ER questions were asked again; the other 106 test answers are the first run's. What's left on test is one retrieval miss (the latest lipid panel wasn't retrieved, and the model said it found no values) and one wrong comparison that the judge caught ("higher values" when one of the four was lower). [docs/evals.md](docs/evals.md#the-test-split) has the details.

On dev, the model wrongly said "not in record" once in 141 answerable questions. The judge went through three versions. The first scored faithfulness 0.635 because it couldn't check "most recent" claims. 100 sentences labeled blind by Opus 5.5, a stronger model than the judge, put the share of supported sentences at 0.97 to 0.98, against 0.993 to 0.996 from the current judge, which misses answers that leave out entries found only in clinical notes. [docs/evals.md](docs/evals.md#checking-the-judge-against-blind-reference-labels) has the comparison.

## How it works

```
Synthea v4.0.0, pinned (data/synthea/generate.sh)
  -> data/cohort/*.json.gz        15 FHIR R4 transaction bundles, committed
  -> make ingest                  typed views -> one text card per resource
                                  -> SQLite: resources, cards, pinned summary, embeddings
  -> POST /patients/{id}/ask
       1. retrieve   filter to the patient; BM25 + bge-small embeddings fused with RRF;
                     series expansion; pinned summary in front
       2. generate   Claude (claude-opus-5-5), structured output:
                     sentences + cited card ids, or status "not_in_record"
       3. check      citations to anything outside the context are removed and reported
       4. respond    answer, citations with resource URLs, retrieved cards, usage, cost, latency
```

The design decisions and the reasons for them are in [docs/design.md](docs/design.md) (D1 to D18), with what changed during the build and what comes next.

## Quickstart

Needs [uv](https://docs.astral.sh/uv/). Java 17+ only if you regenerate the cohort.

```bash
make setup     # .venv from uv.lock
make ingest    # build data/index.sqlite; the first run downloads the embedding model (~70 MB)
make serve     # http://localhost:8000/docs
```

To get answers from `/ask`, put `ANTHROPIC_API_KEY` in `.env` (see `.env.example`), or set `FHIR_RAG_LLM_BACKEND=cli` to use a logged-in Claude Code CLI on a Claude subscription instead. Everything else works without either.

```bash
curl -s localhost:8000/patients
curl -s -X POST localhost:8000/patients/<patient-id>/ask \
  -H 'content-type: application/json' \
  -d '{"question": "What was the most recent hemoglobin A1c, and when?"}'
```

With Docker: `docker compose up --build`. The container builds its index on first start (about 15 minutes on a laptop CPU, mostly embedding 42,000 cards) and keeps it in a volume.

## Evals

```bash
make eval-retrieval              # deterministic, free; SPLIT=test for the held-out split
make eval-selftest               # oracle and null answers through the whole harness, offline
make eval-answers RUN=pilot      # real model calls; costs money (see below)
```

`run_answers` writes one line per question as it finishes, resumes an interrupted run, sends failed attempts to `errors.jsonl` instead of scoring them as wrong, and stops at `--spend-cap` dollars (default 10). The dev split measured $0.0275 per question to answer and $0.015 per answer to judge, about $6.60 for the 164 dev questions it ran on. `make eval-rejudge FROM=<run> RUN=<new-run>` re-grades stored answers with the current judge, which costs only the judge calls. With `FHIR_RAG_LLM_BACKEND=cli`, both go through the Claude Code CLI and use a Claude subscription's limits instead of API credits ([how that differs](docs/evals.md#running-on-a-claude-subscription)).

CI (`.github/workflows/ci.yml`) runs lint, strict mypy, tests and the retrieval eval on every push, and fails on any cross-patient leak or on a drop of more than one question in recall@10, hit@10 or MRR against `evals/baselines/retrieval-dev.json`. The answer eval runs on demand and on pull requests labeled `llm-eval` (`.github/workflows/llm-eval.yml`), with the API key as a repository secret. It reports numbers without a pass/fail threshold, because run-to-run noise hasn't been measured yet.

## Layout

```
src/fhir_rag/
  fhir/        loader, typed views, notes, cards
  retrieval/   bm25, dense, fusion, pinned summary, retriever
  llm/         clients (API, Claude Code CLI), answer service, prompts, pricing
  api/         FastAPI app, schemas, JSON logs
  evals/       question templates, metrics, retrieval and answer runners, judge, calibration
  ingest.py    build the index
data/          synthea/ (pinned generation), cohort/ (committed bundles)
evals/         questions/, baselines/, reports/
docs/          design.md, data.md (cohort profile), evals.md
```

## Limitations

- Synthea's clinical notes are generated from the structured record, so they repeat facts that are already in other resources. Results on real clinician notes would differ.
- All 275 questions come from templates whose gold labels are computed from the raw bundles. There are no hand-written questions yet, so wording varies less than real use would.
- Each answer number comes from one run. Run-to-run noise isn't measured, so small differences between dev and test, or between two runs, mean little.
- BM25 has no stemming. "Does the patient smoke?" misses the card that says "Never smoked tobacco"; most of the remaining retrieval misses are that question.
- The pinned summary puts about 28 cards in front of every question (about 38 cards in all). That's affordable at this scale, and the same-budget comparison above shows the gain isn't just from the extra cards.
- One patient per question. Questions across patients, such as cohort queries, are out of scope.
- No authentication. With real PHI this would need SMART on FHIR authorization (scopes such as `patient/Observation.rs`), a BAA with the model provider, and an access audit log kept apart from the application logs. The logs here already carry no question or record text.
